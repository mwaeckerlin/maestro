# Features

Numbered register of every feature of the image; a number is never reused. Every feature is covered by tests listed in [TESTS.md](TESTS.md); the guard `tests/docs-contract.sh` fails when a feature has no test.

- **F1 — Maestro without Pinokio.** The image runs the installation steps of the upstream Pinokio launcher (`install.js`, `torch.js`): the Python environment, `requirements.txt`, PyTorch with xformers and Triton, the optional acceleration and GGUF kernels, the voice-conversion component `maestro-seedvc` and the React interface. Every version comes from the upstream launcher files at build time, so the image follows each upstream release without a version number of its own. `MAESTRO_SOURCE` (build argument) names the upstream repository and branch, default `https://github.com/Blizaine/Maestro.git#main`.
- **F2 — Headless runtime.** The final stage is `mwaeckerlin/ubuntu-scratch`: no shell, no package manager, no interpreter besides the Python Maestro runs on; the service runs as the unprivileged user `somebody` of that base and the code of the image is read-only for it.
- **F3 — CUDA 13 runtime of upstream.** The image carries upstream's "H3 Sol Engine / CUDA 13" runtime, the one upstream uses on Linux for every GPU from RTX 40 on, including the Blackwell generation of the NVIDIA GB10. The NVIDIA container toolkit hands the GPU and driver to the container (`NVIDIA_VISIBLE_DEVICES`, `NVIDIA_DRIVER_CAPABILITIES`).
- **F4 — Bind address from the environment.** `MAESTRO_HOST` (default `0.0.0.0`) and `MAESTRO_PORT` (default `42003`) set where the server listens; a port that is no number between 1 and 65535 stops the start with a message naming the variable.
- **F5 — Model directory.** `MAESTRO_MODEL_DIR` (default `/models`) receives the model weights, the LoRAs (`loras/`) and the HuggingFace cache (`HF_HOME`); it is a cache that can be deleted and downloaded again.
- **F6 — Output directory.** `MAESTRO_OUTPUT_DIR` (default `/output`) receives every generated image, video and audio file.
- **F7 — State directory.** `MAESTRO_STATE_DIR` (default `/state`) receives everything else Maestro writes: settings, projects, the queue it saves after a crash, which contains prompts. Maestro runs from a copy of its app directory there; the code of the image replaces the code in the copy at every start and keeps what Maestro wrote. A tmpfs at `/state` keeps all of it off the disk.
- **F8 — Maestro settings from the environment.** `MAESTRO_CONFIG`, a JSON object, is merged into Maestro's own `wgp_config.json` at every start, nested objects key by key. Where the file does not exist yet, Maestro creates it first with its hardware auto-tune, then the values are merged on top. Invalid JSON or a value that is not an object stops the start with a message naming the variable.
- **F9 — Served below a path prefix.** Behind a reverse proxy that routes a prefix such as `/spark-4d3f/maestro` to the container and strips it, the interface works unchanged: a script loaded first by the interface puts the prefix in front of every root-absolute URL it requests (fetch, element `src` and `href`, `window.open`, the service worker), the server takes the prefix from `X-Forwarded-Prefix` as ASGI `root_path` for the classic Gradio interface, and a redirect to a root-absolute address keeps the prefix. Served at the root, nothing changes. A prefix header that is not a plain path is ignored.
- **F10 — Programs of the runtime.** `ffmpeg` and `ffprobe` for the media pipeline, `gcc` with the C library headers for the kernels Triton compiles on first use, `git` for plugin installation, and `/sbin/ldconfig` as a binary, which Triton and `ctypes` run to find libraries.
- **F11 — arm64 for the NVIDIA GB10.** The image is published for `linux/amd64` and `linux/arm64`. On arm64 the upstream pins PyPI publishes for x86_64 Linux only are replaced: `onnxruntime-gpu` by its latest release, `decord` by `decord2`, `taichi` by `gstaichi` under the module name `taichi`, and the PyTorch CUDA 13 index is added for `torchcodec`, together with `nvidia-npp`. The `torch.js` wheels that exist for x86_64 only, `xformers` and the optional kernels, are skipped and named in the build log; Maestro's attention code runs without `xformers`. The installed list is kept in the image, and `npm run test:arm64` measures on any build host whether the arm64 set resolves.
- **F12 — Nothing leaves the container unasked.** Telemetry of HuggingFace and Gradio is off (`HF_HUB_DISABLE_TELEMETRY`, `GRADIO_ANALYTICS_ENABLED`, `DO_NOT_TRACK`), and the Tailscale route the Pinokio launcher refreshes at every start is not started.
- **F13 — Health check.** The image declares a `HEALTHCHECK` (`maestro_serve.py --health`): healthy once the interface at `/` answers, which Maestro mounts as the last step of its start. The start period is 15 minutes, because the first start imports the engine and builds the model registry. Docker, Compose and Swarm read it without configuration.
